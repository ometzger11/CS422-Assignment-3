# A3 report figures and tables

All files here are generated from `results/a3/runs.csv` and `samples.csv` by
[`client/report_plots.py`](../../../client/report_plots.py), which reuses
[`client/plots.py`](../../../client/plots.py). Run from `client/`:

```sh
python3 report_plots.py --runs ../results/a3/runs.csv --samples ../results/a3/samples.csv \
    --env ../results/a3/environment.txt --rep-server 185.76.9.135:5201 --out ../results/a3/report
```

Each figure is a `.pdf` (for LaTeX) and a 200 dpi `.png` (for Docs or Word).
`path_rtt_probe.txt` is the only file not generated by the script: it is the raw
output of a ping/tracepath probe, taken by hand after the batch.

## Explaining the differences: talking points with numbers

1. **Throughput.** Mean goodput per run is BBR 60.4 [95% CI 45.9, 75.6],
   Reno 57.9 [47.2, 69.9], CUBIC 31.2 [19.1, 45.0] and DART 28.5 [16.0, 42.8]
   Mbit/s. The median runs are 46.9, 46.5, 16.3 and 7.1. Reno and BBR were each
   best on 5 of the 10 destinations.
2. **The gap comes from stalled runs, not from a lower steady rate.** DART had
   15 of 30 runs below 5 Mbit/s, CUBIC 8, BBR 1 and Reno 0. The ordering is the
   same with a 2 or 10 Mbit/s threshold. The 15 DART runs that did not stall
   averaged 55.5 Mbit/s; on the same destination, that is a median of 0.85× Reno.
   Fig. 1 shows both cases on one server: DART rep 1 reaches about 160 Mbit/s
   like Reno, while reps 2 and 3 never leave cwnd ≈ 20–160.
3. **Why DART and CUBIC stall (Fig. 4).**
   - **The path.** On this VM's internet path, RTT is inflated while the sender
     is slow. In the stalled runs, sRTT in the first second was 27–144 ms
     (median about 80 ms) above the base RTT while cwnd was still tens of
     segments. That is not the sender's own queue: 80 ms at 40–100 Mbit/s would
     need 280–690 queued segments. Idle pings with no TCP flow show the same
     jitter, starting at the first ISP hop past the LAN router
     (`path_rtt_probe.txt`; 100.69.2.1: min 1.8 ms, max 202 ms).
   - **DART** treats any delay above HIGH (≤ 20 ms) as a queue. It leaves slow
     start early: the batch counters show 28 slow-start exits on delay and 28
     loss responses. Rule C then cuts cwnd by 10% per round while the rate does
     not improve (397 decreases in the batch).
   - **CUBIC's HyStart** exits slow start when the RTT rises by more than
     min RTT/8 (clamped to 4–16 ms), so the same delay ends its slow start
     early. From that small window, its cubic growth is slow at first.
   - **Reno** ignores delay. It slow-starts until loss or until cwnd stops
     growing at about 3,900–4,000 segments, which is visible on many destinations and
     is most likely the receiver's window (`rwnd_limited` was not logged).
   - **BBR** sizes cwnd from its bandwidth and min-RTT estimates, so delay noise
     does not end its startup.
4. **RTT.** Median sRTT is similar for every algorithm (202–233 ms) because base
   RTTs of 56–244 ms dominate. The tails differ: p95 sRTT − min RTT is CUBIC
   584, Reno 429, BBR 337 and DART 293 ms. DART has the lowest p95 queueing
   delay, which fits its delay-based back-off. Its median (69 ms) is no lower
   than Reno's or CUBIC's (72 ms), though, because much of that delay is the
   access link's and is present even when cwnd is tiny.
5. **Loss signal.** Retransmitted segments per run: BBR 46.7, Reno 17.1, CUBIC
   7.5, DART 3.8. BBR's startup and probing overshoot buffers the most; DART
   rarely fills a buffer, because it backs off on delay before loss.
6. **Caveats.**
   - 10 s tests on paths with 56–244 ms base RTT are only about 40–180 RTTs, so
     startup dominates.
   - There is one client vantage point, and its access link is noisy.
   - There are 3 repetitions per destination.
   - The path probe was taken after the batch, not during it.
   - The 5 Mbit/s stall threshold is a choice; the ordering holds at 2 and 10.
   - DART's counters are global, so they cannot be split per run.
